検索の方式（キーワード・ベクトル・ハイブリッド・セマンティック）を、質問と正解の文書で測り、表で比べます。武将・人事・ホテルを、同じ道具・同じ形の質問で測ります。検索するだけで、何も作らず、何も変えません。

nDCG と再現率の考え方は、基礎編の 05 とハンズオン資料の評価です。質問の形と種類は evaluation/README.md にあります。

何を測るか

  • 質問ごとに、取ってくるべき文書（正解）が、上位 k 件に入ったかを見ます（k は既定で 10）。
    • nDCG@k：正解が上にあるほど高い（0〜1）
    • 再現率@k：正解のうち、上位 k 件に入った割合
    • 1位：1位が正解だった質問の割合
  • 人事の権限の質問（種類 permission、12問）は、9問に正解の文書がなく（その人に見える文書がない）、3問は求人票が正解です。正解のない質問は、平均に入れず、見えてはいけない文書が上位 k 件に出た数（漏れ）で数えます。正解のある3問は、平均にも入れ、漏れも数えます。漏れは 0 であるべき数です。
  • 方式は4つです：keyword・vector・hybrid・semantic（ハイブリッド＋セマンティック ランカー）。ホテルの condition の質問は、各方式に絞り込みを足した +filter（例 hybrid+filter）も測ります。
  • 数えるのは文書の単位です。人事は1つの文書が多くのチャンクになりますが、同じ文書は1回だけ、最初に出た順位で数えます。

1. 測る前に

構築する人：

  • 測るデータのインデックスを作ってある
    • 武将：sengoku（武将の 01。ベクトルは 03）
    • 人事：hr-docs（応用（人事）の「最初に1回」）
    • ホテル：hotels-blob（ホテルの 2 章）と hotels-cosmos（5 章）。keyword が hotels-blob、vector と hybrid が hotels-cosmos を検索します
  • python tools/team.py health で、インデックスの文書の数を見る（az にサインインした PC で実行します。メンバーは実行できません）
    • 目安：sengoku 150、hr-docs 23 以上（文書 23 から作ったチャンクの数）、hotels-blob 50、hotels-cosmos 50
    • 目安と違うときは、測る前に直します（正解の文書が索引にないと、点が下がります）
  • 人事で、応用編の 17 を試したあとなら、applied/topics/17-update-delete/ のフォルダーで python cleanup.py を実行して、文書を元に戻す（構築する人の .env.local で）
    • 旧い版の求人票 JOB-REQ042-v1 が索引に残っていると、一般社員の「漏れ」に数えられます

メンバーも、構築する人も：

  • .env.local を Repo 直下に置く（検索だけのキーでよい。Azure の準備の 4）
  • ホテルを測るときは、ホテルのデータの JSON を、ホテルの 4-3 のとおり _work/hotel-vectors/ に置く（別の場所なら、次の手順に --hotel-data <JSON の場所> を足します）

pip で入れるものはありません（標準ライブラリだけです）。Windows で python が見つからないときは py に替えます。

2. 測る順番

  1. 質問を確かめる（通信しません）

    python tools/check_questions.py --dataset hr
    • 「問題なし（60 問）」と出れば進みます。--dataset は sengoku・hr・hotel
    • ホテルは、データの場所を渡します：python tools/check_questions.py --dataset hotel --hotel-data <JSON の場所>（_work/hotel-vectors/ にあれば省けます）

  2. 方式ごとに測る。最初は数問だけで試します

    python tools/eval_search.py --dataset hr --limit 6
python tools/eval_search.py --dataset hr
    • --limit 6：先頭の6問だけ。人事は 6 の倍数、ホテルは 5 の倍数なら、質問の種類がそろいます
    • 画面に、質問ごとに1行（正解のある質問は nDCG、権限の質問は漏れの数）、最後に方式ごとの平均と、使った量（検索・セマンティック ランカーの回数、質問の埋め込みのトークン）が出ます
    • 結果は _work/eval/<データ>-<時刻>.json に書かれます（Git に入りません）。最後の「結果：」の行が、そのパスです
    • 人事・武将は、全部の質問・4方式で検索 240 回（うちセマンティック ランカー 60 回）です。セマンティック ランカーの無料枠は月ごとで、チームの AI Search 全体で使います。全部を測るのは、チームで1回にします
    • 方式を絞る：--methods keyword,hybrid。上位何件で採点するか：--k 5

  3. 結果を表にまとめる

    python tools/eval_report.py _work/eval/<結果のファイル>.json
python tools/eval_report.py _work/eval/<結果のファイル>.json --md _work/eval/report.md
    • 結果のファイルを2つ以上渡すと、同じ表の中で横に並べます（同じデータの結果だけ）。名前は --label で付けます
    • --md は、表を Markdown にも書きます

止まったとき、飛ばしたとき：

  • チームがまだ作っていないインデックスや、設定のない方式（ホテルの semantic。手順書のインデックスに、セマンティックの設定がありません）は、その方式だけ飛ばして、理由を出します。ほかの方式は最後まで測ります。表にも「飛ばした」と出ます
  • 「エラー 403」で止まったとき：キーが合っているか、セマンティック ランカーの無料枠を使い切っていないかを確かめます。そこまでの結果は保存されます
  • 終了コード：0 は測れた、1 は止まった（そこまでの結果は保存）か、測れた方式がなかった、2 は質問・データ・引数が使えない

3. 結果の読み方

表は2つ出ます。

  • 「方式ごと」：行は方式。列は、問（平均に入れた質問の数。測った数と違うときは「平均に入れた数/測った数」）・nDCG@k・再現率@k・1位。人事は、漏れ問（漏れがあった質問の数）・漏れ文書。さらに、検索・セマンティック ランカーの回数、埋め込みのトークン、費用の見込み
    • 方式の行のあとに、「埋め込み（共通）」の行（質問の埋め込みを使ったとき。方式で共用するので、ここにまとめます）と、「合計」の行（全部の回数と費用）が付きます
  • 「方式×質問の種類」：行は質問の種類、列は方式。値は nDCG@k の平均で、カッコの中は問の数

見る順番：

  1. 「方式ごと」で、全体の強さを見る。方式の差が小さければ、次の表へ
  2. 「方式×質問の種類」で、得意・不得意を見る。全体の平均が同じでも、種類で分かれます
    • 例：番号や固有名詞はキーワードが強く、言い換えはベクトルが強く、条件（ホテルの評価・駐車場など）は +filter を足した方式が強い、という見込みがあります。見込みどおりかは、自分で測って確かめます
    • カッコの問の数が少ない種類は、1問で平均が大きく動きます。数を見てから判断します
  3. 人事は、漏れを見る。一般社員の質問で漏れが1以上なら、権限の絞り込みか、索引の文書が違っています（応用編の 16）。漏れが出た質問と方式は、測っている最中の画面に出ます

「-」は、正解のない質問だけの種類か、測っていない方式です。人事の permission は、正解のある3問だけの平均になります（カッコの中も3）。

4. 費用の見込みと、単価のファイル

費用の見込みは、使った回数 × 単価です。単価は、この Repo に書いていません（変わるため）。料金のページで確かめた値を、自分で書きます。

  1. config/prices.example.json を config/prices.json に写す（config/prices.json は Git に入りません）

    Copy-Item config/prices.example.json config/prices.json

  2. 料金のページで、次の単価を確かめて書く（ページの場所は、ファイルの sources にあります：AI Search の料金、Azure OpenAI の料金）

    • semantic_per_1000：セマンティック ランカー 1,000 回の単価
    • embedding_per_1m_tokens：埋め込み（text-embedding-3-small）100 万トークンの単価
    • search_per_1000：検索 1,000 回の単価。Basic の AI Search は時間で課金され、回数では増えないので 0
    • currency：料金のページの通貨（円なら JPY）。checked：単価を確かめた日の文字
    • ページの単位が違うときは、上の単位に直して書きます

書いたあとで、eval_report を実行し直します。

  • 費用の列に、金額が出ます。検索は、セマンティックを除いた回数に search_per_1000 を掛けます
  • 質問の埋め込みは、質問ごとに1回を方式で共用するので、「埋め込み（共通）」の行に分けて出ます
  • 単価が空（null）のままのときは、回数だけ出して「単価が未設定」と書きます。0 円とは書きません。一部だけ書いたときは、書いた分だけを足して、金額に「＊」が付きます（合計ではありません）
  • この費用に入るのは、検索・セマンティック ランカー・質問の埋め込みだけです。LLM に渡す文書の分は入りません（下の演習 B）

5. 演習：精度と費用の釣り合い

測った数字で、次の2つを決めます。数字は、自分のチームの AI Search で測ったものを使います。

演習 A：セマンティック ランカーを使うか

  1. 同じ質問・同じ k で、使わない方式（hybrid）と使う方式（semantic）を、1回で測る

    python tools/eval_search.py --dataset hr --methods hybrid,semantic

  2. eval_report の「方式ごと」で、hybrid と semantic の行を比べる

    • 良くなった分：nDCG@10・再現率@10・1位の差
    • 増えた費用：「セマンティック」の回数と、費用の見込みの差
  3. 「方式×質問の種類」で、差が出た種類を見る。全体で差が小さくても、ある種類だけ大きく上がるなら、その種類の質問が多い業務にだけ使う、という決め方もあります
  4. 実際に使うときの月の費用を、自分で見積もる：月の質問数 × semantic_per_1000 ÷ 1,000（無料枠の中なら増えません。枠を超えたあとの単価は、料金のページで確かめます）
  5. 「差がこれ以上なら使う」という基準を、先に決めてから、使う・使わないを決める（基準は、業務で許せる外れの量から決めます）

演習 B：上位何件を LLM に渡すか

  1. 演習 A で選んだ方式を、k を変えて、同じ質問で3回測る（ここでは hybrid の例。semantic を選んだときは、3回でセマンティック ランカーを質問の数の3倍使うので、無料枠を確かめてから測ります）

    python tools/eval_search.py --dataset hr --methods hybrid --k 3
python tools/eval_search.py --dataset hr --methods hybrid --k 5
python tools/eval_search.py --dataset hr --methods hybrid --k 10

  2. 3つの結果を、横に並べる

    python tools/eval_report.py _work/eval/<k が 3 の結果>.json _work/eval/<k が 5 の結果>.json _work/eval/<k が 10 の結果>.json --label k3 --label k5 --label k10

  3. 再現率@k を見る。k を増やすと、正解が入る割合は上がりますが、ある所から伸びなくなります。伸びなくなった最初の k が、渡す件数の候補です

  4. 表の費用は、k では変わりません（検索の回数が同じです）。k の費用は、LLM に渡す文書の分です。自分で見積もる：月の質問数 × k × 文書1件のトークン数 × LLM の入力の単価（1 トークンあたり）
  5. 渡す件数を決める。k を小さくすると、費用は減りますが、正解を渡し損ねる質問が増えます。k を大きくすると、渡す文書が増え、費用も、無関係な文書も増えます

2つの演習のあとで、次の3行を書いて残します。

  • 選んだ方式と k
  • 根拠にした数字（自分で測った表のどの行か）
  • 月の費用の見込みと、その計算

6. 自分の組織のデータで質問を作る

評価の質問を作る手間が、測るときのいちばんの手間です。手順は、この Repo の人事とホテルの質問を作ったときと同じです。

  1. 1問を、evaluation/README.md の形で書く
    • 必ず書く：qid（質問の番号）・question（検索に使う質問の文）・type（種類）・answer_ids（取ってくるべき文書の ID。空にしてよいのは permission だけ）
    • why（どの文書のどこに答えがあるか）は、書かなくてもかまいません
    • evidence（答えの根拠になる、本文にそのまま出る短い語句）は、人事と、ホテルの condition でない質問には要ります（武将は任意）
    • permission には、as_role（だれとして聞くか）と hidden_ids（その人に見えてはいけない文書の ID）が要ります
  2. 質問の種類を分ける。業務で起きる聞き方を、種類ごとに数問ずつ作る（この Repo は、1種類 6〜12 問）
    • 例：文書に出てこない言い換えの語で聞く、番号や人名・社名で聞く、金額・日付・点数の条件で聞く、答えが2つ以上の文書にまたがる、画像だけの文書にしか答えがない、聞く人に見せてはいけない文書がある（権限）
    • 種類を分けると、「方式×質問の種類」の表で、得意・不得意が見えます
  3. 正解の文書を決める。答えが書いてある文書を、すべて入れる（どれが上位に出ても正解です）。権限の質問は、見える文書だけを answer_ids に入れ（なければ空）、見えてはいけない文書を hidden_ids に書く
  4. check_questions で、形・ID・種類の数・根拠の語句を確かめる（通信しません）

  5. 人が、抜き取りで確かめる。質問の一覧を1枚の HTML にして、ブラウザで開く

    python tools/spot_check.py --dataset hr --n 10 --seed 1 --out _work/spot-hr.html
    • 種類ごとにほぼ均等に N 問を選び、問・種類・正解の文書（根拠の語句を黄色で強調）を1つの画面に出します。通信しません
    • 1問ずつ「正しい」か「直す」を付け、メモを書き、「Markdown に書き出す」で結果を残します
    • 「直す」の問を直したら、4 から繰り返します。--seed を変えると、別の問が選ばれます
    • ホテルは --dataset hotel（--hotel-data も）、武将は --dataset sengoku

この Repo の道具は、武将・人事・ホテルの3つのデータの設定を持っています。自分の組織のデータで動かすときは、構築する人が、3つと同じ形で、次の場所に足します。

  • tools/evallib/datasets.py：SPECS に、インデックスと、方式ごとの検索先、文書の ID の項目などを足す
  • tools/evallib/questions.py
    • DATASETS（データの名前）、TYPE_TARGETS（質問の種類と、種類ごとの数。足さないと、武将の5つの種類だけが使えます）
    • QUESTION_FILES（質問のファイル）、DATA_FILES（文書のデータ）、ids_of（データから文書の ID を取り出す）
    • 必要なら、データ固有の確かめ（@dataset_check("名前")）
  • tools/spot_check.py：DATASET_LABEL（一覧の見出し）、DOC_BUILDERS と build_context（正解の文書を、本文つきで出す）。種類の表示名 TYPE_LABEL は、足さなくても動きます

質問のファイルは、evaluation/<データの名前>_questions.json に置き、QUESTION_FILES に書きます（hr_questions.json と同じ）。組織の文書や質問を公開の Repo に入れてはいけないときは、_work/ の下か Repo の外に置き、--file で渡します（_work/ は Git に入りません）。

つまずいたとき

  • 「.env.local が読めません」などの設定の案内が出る：Repo の直下で実行しているか、.env.local があるかを確かめます。キーは .env.local だけから読みます（端末の環境変数は読みません）
  • 「インデックス … がありません」と出て、その方式が飛ばされる：構築する人が、そのインデックスを作ってあるか確かめます（python tools/team.py health）
  • ホテルの semantic が飛ばされる：手順書のインデックスにセマンティックの設定がないためで、正常です
  • 人事の一般社員の漏れが 0 にならない：17 を試したあとなら、cleanup.py で元に戻してから測り直します
  • 「単価が未設定」と出る：config/prices.json を作って、単価を書きます（4）
