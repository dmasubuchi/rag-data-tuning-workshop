# 検索の評価で使う質問

検索の方式を比べるための質問と、正解の文書の番号です。3つのデータ（武将・人事・ホテル）が、同じ形の質問を使います。質問の中身を足す・直すのは進行役か構築する人です。メンバーは、できあがった質問を読んで評価を動かすだけです。

測る順番（質問を確かめる、方式ごとに測る、表にまとめる）と、結果の読み方、精度と費用の釣り合いの演習は、[手順書の評価](../guide/evaluation.md)にあります。

## ファイル

- 武将：`basic/data/sengoku/questions.json`（既存の60問。直さない）
- 人事：`evaluation/hr_questions.json`（60問）
- ホテル：`evaluation/hotel_questions.json`（40問）

どれも質問の並び（JSON の配列）です。人事とホテルのファイルはできています。ホテルのデータは Repo に写していないので、ホテルの質問を確かめるときは、データの場所を渡します（下の「質問を確かめる」）。

人事の60問は、種類をまぜて並べてあります。`hr-01`〜`hr-36` は、6問ごとに6つの種類が1回ずつ（`paraphrase`・`proper-noun`・`numeric`・`multi-doc`・`scan`・`permission` の順）です。`scan` は6問で尽きるので、`hr-37` 以降は5つの種類で回り、最後の4問は `paraphrase` と `permission` だけです。先頭から何問かだけ取るときは、6の倍数の問数（6・12・…・36）なら、6種類がそろいます。

ホテルの40問も、種類をまぜて並べてあります。`hotel-01`〜`hotel-30` は、5問ごとに5つの種類が1回ずつ（`paraphrase`・`proper-noun`・`condition`・`ja-en`・`amenity` の順）です。`hotel-31` 以降は、数の多い `paraphrase`・`condition`・`amenity` だけです。先頭から5の倍数の問数（5・10・…・30）なら、5種類がそろいます。

## 1問の形

次は書き方の見本です。**実際の `hr-01` ではありません**（`hr_questions.json` にもありません。本物の質問は、そのファイルを読みます）。

```json
{
  "qid": "hr-00",
  "question": "REQ-042 の今の求人票で、年収はいくらからいくらまでですか。",
  "type": "numeric",
  "answer_ids": ["JOB-REQ042-v3"],
  "evidence": {"JOB-REQ042-v3": "600万円から800万円"},
  "why": "年収は JOB-REQ042-v3 の本文にある。"
}
```

必ず書くもの：

- `qid`：質問の番号。ファイルの中で1つだけ。`hr-01` のように、データの名前と連番にします（空白は入れません）
- `question`：検索に使う質問の文
- `type`：質問の種類（下の「種類」）
- `answer_ids`：取ってくるべき文書の ID の並び。答えが書いてある（索引に入る）文書を、すべて入れます（どれが上位に出ても正解です）。文書の ID は、武将は `bushou.json` の `id`、人事は `applied/data/manifest.json` の `files[].doc_id`、ホテルはホテルのデータの `HotelId`（文字列）。**空（`[]`）でよいのは `permission` だけ**です。答えの文書が1件もない質問で、`permission` の説明を見てください。ほかの種類で空だと、確かめの道具が問題にします

必要なときだけ書くもの：

- `why`：どの文書のどこに答えがあり、どの方式が得意・不得意になりそうか
- `evidence`：`answer_ids` と `hidden_ids` の文書ごとに、答えの根拠になる短い語句。`{"MAIL-01": "一次面接の日程の候補を2つ"}` の形で、語句は、その文書の本文にそのまま出るものにします。**人事の質問と、ホテルの `condition` でない質問には要ります**（武将は任意）。確かめの道具が、本文のもと（人事は下の「人事の決まり」、ホテルは「ホテルの決まり」）にその語句があるかを調べます。ホテルは、`{"6": ["無料Wi-Fi", "バー"]}` のように、語句の並びで書いてもかまいません（並びの語句は、全部あること）。質問を目で確かめる抜き取りの一覧にも、この語句を出します
- `note`：作る人のメモ
- `as_role`：だれとして聞くか（例 `"role:employee"`）。`permission` の質問に要ります
- `hidden_ids`：その人には見えてはいけない文書の ID の並び。`permission` の質問に要ります（1件以上）
- `condition`：ホテルの質問で、答えの条件を表したもの（例 `{"Rating": {"ge": 4.5}, "ParkingIncluded": true}`）。種類 `condition` の質問に要ります。書き方は「ホテルの決まり」

ほかの項目（武将の `query_terms`・`avoid_terms`・`clues` など）があっても構いません。評価は読み飛ばします。

武将の既存の60問は、種類を `type` でなく `intent` と書いています。直さずに、`intent` を `type` として読みます（`load_questions` が読み替えます）。

## 種類

武将（既存の `intent`。数は確かめません）：

- `keyword-wins`：キーワード検索が上に出し、ベクトル検索は外す見込みの質問
- `vector-wins`：ベクトル検索が上に出し、キーワード検索は外す見込みの質問
- `hybrid-improves`：キーワードとベクトルを合わせる（ハイブリッド）と、どちらか一方より良くなる質問
- `hybrid-worsens`：ハイブリッドにすると、片方だけが1位にしていた正解が落ちる質問
- `climax`：キーワードもベクトルも正解を外し、セマンティック ランカー（意味での並べ直し）で上がる見込みの質問

人事（60問）：

- `paraphrase` 12：文書に出てこない言い換えの語で聞く
- `proper-noun` 10：応募番号・求人番号・人名・社名で聞く
- `numeric` 10：年収・日付・点数の条件で聞く
- `multi-doc` 10：答えが2つ以上の文書にまたがる
- `scan` 6：画像だけのスキャン（OCR が要る）に答えがある
- `permission` 12：聞く人に見せてはいけない文書がある（下の説明）

ホテル（40問）：

- `paraphrase` 10：文書に出てこない言い換えの語で聞く
- `proper-noun` 6：ホテル名・地名などの固有名詞で聞く
- `condition` 10：評価・駐車場・部屋の料金などの条件で絞る
- `ja-en` 6：日本語で聞いて英語の項目にしか答えがない（またはその逆）
- `amenity` 8：設備（`Tags`・`Tags_ja`・部屋の説明）で聞く

人事とホテルは、種類ごとの数が上の数と同じでなければ、確かめの道具が問題にします。文書が足りない種類は、数を減らして報告します。

### 種類の目標を変えるとき

文書が足りずに数を減らす（ほかの種類に回して合計を保つ）ときは、次の4か所をそろえます。

1. `tools/evallib/questions.py` の `TYPE_TARGETS`
2. この README の「種類」の数
3. `tests/test_questions.py` の `test_targets_match_the_brief`（人事は `HrQuestionsTest.test_hr_questions_pass` の数も）
4. 質問のファイル（新しい数に合わせて、質問を足す・直す）

そろえたら、下の「質問を確かめる」を実行します。

### 人事の決まり

人事は、種類ごとの決まりがあり、確かめの道具が見ます。

- 正解の文書の ID は、`applied/data/manifest.json` の23件。旧い版の求人票（`JOB-REQ042-v1`）は索引に入らないので、正解にしません
- `answer_ids` には、答えが書いてある文書を、すべて入れます。同じことが経歴書にも評価一覧にも書いてあれば、両方です。ただし、質問の文が文書の種類を名指しする（「経歴書に」「メールで」「求人票から」）ときは、その種類の文書だけを入れます（どれを名指ししたかは、質問を読めば分かるように書きます）
- `multi-doc`：`answer_ids` は2件以上で、2つ以上の別の文書にある事実が、それぞれ要ること（どれか1件だけでは答えきれません）
- `evidence`：`answer_ids` と `hidden_ids` の文書ごとに1つ。語句は、その文書の本文のもとに、そのまま出るものにします（空白と改行は無視して探します）。本文のもとは `applied/data/_build/content/` です
  - 求人票・経歴書：`jobs/*.md`・`resumes/*.md`
  - メール：`mail.json` の件名と本文
  - 面接の評価の一覧：`evaluations.json` と `source_ats.json`（選考状況・選考履歴のシートの元の台帳）
  - スキャン：`scans.json` の、そのスキャンの記述と、画像を描く `_build/make_scans.py` の、そのスキャンを作る関数（`make_memo` など）を探します。どちらも文字として読むだけで、`make_scans.py` は動かしません（確かめの道具は標準ライブラリだけで動きます）。画像には日付が `2026.10.26` のように印字されるので、`scans.json` の記述にある `2026-10-26` の形の日付は、`2026.10.26`・`2026/10/26`・`2026年10月26日`・`10月26日`・`10/26`（月日のゼロ埋めあり・なし）でも探します。応募番号（`APP-0471`）や FAX の上部の時刻（`10:52`）は、`scans.json` の記述にそのまま出ます
  - 本文のもとのフォルダーがないときは、語句を探す確かめだけが飛ばされます（語句がそろっているかは見ます）。そのとき、確かめの道具は「本文が見つからないので、evidence の照らし合わせを飛ばしました」と1行出します
  - `mail.json`・`scans.json` の一番上の形が違うとき（`{"mails": [ ... ]}`・`{"scans": [ ... ]}` でないとき）は、質問の問題ではないので、確かめを止めて、理由を1行出して終了コード 2 で終わります。知らない種類のスキャン（`make_…` の関数がない）は、問題の文に出します
- `scan`：`answer_ids` に、OCR が要る文書（manifest の `ocr_required` が true。`SCAN-01`〜`SCAN-03`）を含むこと。スキャンにしか書いていないことを聞きます
- `permission`：次の節

### ホテルの決まり

ホテルの質問も、確かめの道具が決まりを見ます。ホテルのデータは Repo に写していないので、`--hotel-data` で渡したときだけ、データと照らす確かめ（条件の結果・語句の検索・`ja-en` の手がかり）が動きます。データなしで確かめるのは、形・答えの数・`evidence` と `condition` がそろっていることです。

- `answer_ids`：`condition` でない質問は 1〜5 件。`condition` の質問は 1〜20 件で、0 件や 21 件以上になる条件は使いません
- `condition`：答えの条件を、次のように書きます。**質問の意味を条件で表しきれる質問だけ**を、種類 `condition` にします。確かめの道具は、データのうち条件に合うホテルを計算して、`answer_ids` がその全部と同じ集合かを見ます。`answer_ids` は手で数えず、条件から作ります
  - 例：`{"Rating": {"ge": 4.5}, "ParkingIncluded": true, "Category_ja": "ブティック", "Rooms/BaseRate": {"le": 100}}`
  - 値だけ書くと `eq`。`{"演算": 値}` の演算は `eq`・`ge`・`le`・`gt`・`lt`。1つの項目に演算を2つ書けます（`{"Rating": {"ge": 4, "lt": 4.5}}`）。真偽と文字列は `eq` だけです。数は有限の数で書きます（NaN・無限大は使えません）
  - 使える項目：`HotelId`・`Category`・`Category_ja`・`ParkingIncluded`・`IsDeleted`・`LastRenovationDate`・`Rating`、住所の `Address/City`・`Address/StateProvince`・`Address/PostalCode`・`Address/Country`、客室の `Rooms/Type`・`Rooms/Type_ja`・`Rooms/BaseRate`・`Rooms/BedOptions`・`Rooms/SleepsCount`・`Rooms/SmokingAllowed`。検索のインデックスで絞り込める項目だけで、説明やタグでは絞れません
  - `Rooms/…` は「どれかの客室が満たす」です。客室の条件を2つ以上書くと、**同じ客室が全部を満たす**ことになります（100ドル以下の部屋と、禁煙の部屋が別々にあるだけでは、合いません）
  - 改装日（`LastRenovationDate`）は、`{"ge": "2015-01-01T00:00:00Z"}` のように、`T` と `Z`（または時差）つきの日時の文字で書きます。データの日時と同じ順に比べ、検索の `$filter` では引用符のない日時になります
  - 検索の `$filter` の文字は、`tools/evallib/questions.py` の `condition_to_filter` が作ります（例 `Rating ge 4.5 and ParkingIncluded eq true`、`Rooms/any(r: r/BaseRate le 100)`、`Address/City eq 'New York'`）。項目の順は書いた順です。評価の道具が、各方式に絞り込みを足して測るときに使います。`matches(ホテル, condition)` は、データが条件に合うかを返します
- `evidence`：`condition` でない質問は、`answer_ids` のホテルごとに要ります。語句は、そのホテルのデータの文字にそのまま出るものにします（空白は無視して探します）。探す先は、名前（`HotelName`・`HotelName_ja`）・説明（`Description`・`Description_ja`）・カテゴリ・タグ・客室の説明と種類とベッドとタグ・住所です。フランス語の説明、`HotelId`、改装日、位置は、根拠にしません
- `paraphrase`・`proper-noun`・`amenity`：説明・タグを読んで、人が見て正しいと言えるホテルを、すべて入れます。`amenity` は、タグに出ない設備が説明にだけ書かれているホテルも、正解です（例：タグに「無料Wi-Fi」がなくても、説明に書いてあれば入れます）
- `ja-en`：ホテルのデータの英語の項目と日本語の項目（`_ja`）は、説明・タグ・客室の説明が1対1の翻訳で、日本語の項目にしかない手がかりはありません。そこで、**日本語で聞いて、手がかりが英語の項目にしかない**質問を作ります。英語の項目にしかないものは、英語のホテル名（`HotelName`。日本語の項目はカタカナ）、住所（`Address`の都市・州・通り）、客室のタグ（`Rooms/Tags`）です
  - `evidence` の語句に、その手がかりを1つ以上入れます。確かめの道具は、質問の言語（日本語の文字があれば日本語）の項目になく、もう一方の言語の項目にだけある語句が、ホテルごとに1つ以上あるかを見ます。ほかの語句は、どちらの言語の項目にあってもかまいません
  - 英語で聞いて、日本語の項目にしか手がかりがない質問は、データにないので作っていません（その向きの質問を足せば、確かめの道具は通します）

## permission（見えてはいけない文書）

「一般社員として聞いたとき、求人票以外は出てこない」ことを確かめる質問です。

- `as_role` に聞く人の役割、`hidden_ids` にその人には見えてはいけない文書を書きます
- `answer_ids` は、その人に見える正解（なければ空）。`hidden_ids` と同じ ID は入れません
- 空の質問は、再現率の平均に入れません。漏れ（上位 k 件に出た、その役割が見られない文書の数）を、別に数えます
  - 漏れは、文書ごとに1つです（同じ文書が2回出ても1つ）。`hidden_ids` に書いた文書だけでなく、**その役割に見えない文書が上位 k 件に1件でも出れば、1つと数えます**（一般社員なら、求人票でない文書はすべて）。`hidden_ids` は「答えが書いてある文書」の目印で、漏れの数え方を狭めるものではありません
  - 評価のまとめでは、漏れが1件以上あった質問の割合と、漏れた文書の合計を出します
- 人事では、`as_role` は `role:employee`（一般社員）だけを使います。一般社員に見えるのは求人票だけです（`applied/lib/acl.py`）
  - `hidden_ids`：求人票でない文書。その質問の答えが書いてある文書を入れます（求人票は見えるので入れません）
  - `answer_ids`：求人票だけ。求人票で答えられる部分がある質問は、その求人票を入れます。なければ空です

## 質問を確かめる

質問を足したり直したりしたら、Repo 直下で次を実行します。通信はしません。

```
python tools/check_questions.py --dataset sengoku
python tools/check_questions.py --dataset hr
python tools/check_questions.py --dataset hotel --hotel-data <ホテルのデータの JSON>
```

- 問題がなければ「問題なし（N 問）」と出して、終了コード 0 で終わります
- 問題があれば、1件ずつ出して終了コード 1 で終わります。次を見ます
  - 項目の形：`qid`・`question`・`type` は文字列、`answer_ids`・`hidden_ids` は ID の並び
  - qid の重複、使えない種類、文書にない ID
  - `answer_ids` と `hidden_ids` の重なり（同じ ID が両方にあってはいけません）
  - `answer_ids` が空の質問（`permission` 以外）
  - 人事は、`evidence` がそろっていること、語句が本文のもとにあること
  - `permission` の `as_role` と `hidden_ids` の抜け
  - 種類ごとの数の違い
  - 人事は、上の「人事の決まり」（`permission`・`scan`・`multi-doc`）
  - ホテルは、上の「ホテルの決まり」：`condition` の形、`answer_ids` が条件に合うホテル全部であること（データを渡したとき）、答えの数、`evidence` がそろっていて語句がそのホテルにあること、`ja-en` の手がかり
- 質問やデータのファイルが読めないとき（人事の本文のもとの形が違うときも）は、理由を出して終了コード 2 で終わります。質問のファイルがないときは、次の手（`--file` で渡すか、質問を作ります）も出します
- `--file PATH` で質問のファイルを変えられます
- ホテルのデータは、このリポジトリに写していません。ダウンロードした `HotelsData_toAzureBlobs_ja.json` を `_work/hotel-vectors/` に置くか、`--hotel-data` で場所を渡します
- 人事の本文のもと（`applied/data/_build/content`）がないときは、語句を探す確かめを飛ばして、その旨を1行出します
