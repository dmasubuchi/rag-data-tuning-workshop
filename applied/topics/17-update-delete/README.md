# 17 更新と削除

文書は、あとから変わります。応募が取り下げられたら消し、求人票が改訂されたら置き換えます。
Storage のファイルを変えたとき、検索の索引はどうなるか、を確かめます。

このトピックは、**チームの本物の文書**（Storage の入れ物と、インデックス `hr-docs`）を、そのまま直して、**最後に元に戻します**。
写しは作りません。構築する人の画面で動かし、メンバーは見ます。

> **17 の間は、チームの検索の結果も変わります。** 取り下げた応募の書類が検索に出なくなったり、求人票が旧い版になったりする時間があります。
> ほかのメンバーが 15・16・18・19 を動かしていないときに実行してください。最後に元に戻ります（途中で止めたときは `cleanup.py`）。

## 何を学ぶか

- 文書は、Storage の入れ物の直下に、manifest の相対パスのまま置いてある（例 `resumes/CV-APP-0471.docx`）。同じデータソース・同じインデクサー・同じインデックス `hr-docs` に入る
- 削除（`withdraw_application.py`）
  - ファイルを消すだけでは、インデクサーは気づかず、索引に残る（検索に出続ける）
  - blob のメタデータに `IsDeleted=true` を付けて、インデクサーを動かすと、索引から消える。そのあとで blob を消す
  - 索引から消えたことを確かめてから、blob を消す。消えていなければ、blob は残したまま止まって、案内が出る（先に blob を消すと、印を読めなくなる）
  - この教材は、親の文書（blob）の削除を検出すると、射影（index projections）で作った子のチャンクも一緒に消える方式。経歴書とスキャンのチャンクが 0 件になるのを確かめる
    （一般の Blob の削除の説明にある、1つの文書が複数の検索文書になる場合の制限は、射影を使わない方式の話。射影のページ（Microsoft Learn の index projections、Content lifecycle）は、削除の検出で親の削除を検出すれば、子も削除されると書いている）
  - メタデータを足すときは、今のものを読んで残す。`set_blob_metadata` は、指定したもので全部を置き換える
  - 消してしまった blob の取り残しは、同じ名前で `IsDeleted=true` を付けて置き直すと消せる
- 更新（`revise_job_posting.py`）
  - 同じ名前で上書きするだけ。インデクサーが、blob の最終更新日時が前回より新しいことで見つける（設定は要らない）
  - 求人票 REQ-042 の本物（`jobs/JOB-REQ042-v3.pdf`）を、旧い版 v1（チャンク 3 件）の中身で上書きし、v3（チャンク 2 件）で上書きして戻すと、v3 の内容に変わる。余った古いチャンクは残らなかった（実測）
- 元に戻す（`cleanup.py`）
  - manifest の全部の文書が、`applied/data/` のとおりに、Storage とインデックスにある状態にする
  - `data/` と違う（中身かメタデータ。削除の印が付いたままのものも）文書だけ置き直し、manifest にない blob は、削除の印を付けて索引から消えたのを確かめてから消す
  - そのあと、インデクサーを動かし、見てよい人（`allowed`）を付け直す。何度実行しても、同じ結果になる
- 見てよい人（`allowed`）は、インデクサーを動かすたびに、全部のチャンクに付け直す
  - インデクサーが取り込み直したチャンクは `allowed` が空に戻るため（`lib/acl.py` の `sync`。`build_hr_index.py` も同じ）

## 前提

- `pip install -r applied/requirements.txt`（Repo 直下で、仮想環境の中で）
- 構築する人の設定（`python tools/team.py env --role builder`）：AI Search の管理者キーと、Storage の接続文字列が要ります。メンバーの設定では、始めに「この手順は構築する人の設定（--role builder）で実行します」と止まります
- 構築する人が `applied/tools/build_hr_index.py` でインデックス `hr-docs` を作ってあること。データソースは、入れ物の全体を読む設定になっていること（`show_pipeline.py` の 1 で見える）
- v1 の求人票は `applied/data/updates/JOB-REQ042-v1.pdf`（17 だけで使う。`build_hr_index.py` は Storage に置かない）

## 実行

```
python withdraw_application.py       # 応募の取り下げ（削除）。インデクサーを何回も動かすので、数分かかる
python revise_job_posting.py         # 求人票の改訂（更新）。数分かかる
python cleanup.py                    # 途中で止めたときの、元に戻す
```

- どちらも、最初に前の回の途中の状態を元に戻し、`withdraw_application.py` は最後に自分で元に戻す（`revise_job_posting.py` は、最後の手順が元に戻す手順）。何回実行しても同じ結果になる
- `withdraw_application.py --keep` を付けると、最後に元に戻さない（取り下げた状態のまま、Storage や索引を見たいとき）。**そのあいだ、チームの検索から、この応募の書類が消えたままです。** 元に戻すのは `cleanup.py`
- 「インデクサーが実行中なので待ちます」と出たら、そのままお待ちください

## 見るところ

- `withdraw_application.py`（応募 APP-0471 の経歴書・メール・スキャンの 3 ファイル、チャンク 4 件）
  1. いまの「状態」の表：3 つとも Storage に「ある」、チャンクが 4 件。検索で名前が当たる
  2. 失敗：メールの blob を消してインデクサーを動かしても、表の「索引のチャンク」が 1 のまま。「← 取り残し」と出る。検索でも出てくる
  3. 正しい方法：メタデータの「前」と「後」で、`IsDeleted` が足されただけで、ほかは残っている。インデクサーのあと、経歴書とスキャンのチャンクが 0 件になる
  4. 取り残しの掃除：同じ名前で印つきで置き直すと、メールの取り残しも 0 件になり、検索で何も当たらない
  5. 最後に元に戻す：3 ファイルが Storage に戻り、チャンクも戻る
- `revise_job_posting.py`
  1. v1：チャンク 3 件。年収は 500万円から700万円、勤務は週4日出社、「試用期間」の記載がある
  2. 上書き：blob の最終更新日時が新しくなる。v3：チャンク 2 件。年収は 600万円から800万円、週2日出社、「試用期間」はない
  3. 「試用期間」「500万円」で探すと、v1 のときは当たり、v3 では当たらない
  4. v1 にしかない語を含むチャンクは 0 件。チャンクの数が 3 から 2 に減っても、余りは残らない
  5. 最後は、始める前と同じ状態（v3）

## 気をつけること

- 削除の検出は、最初のインデクサー実行から設定しておく。設定する前に消した blob の文書は、あとから設定を足しても、インデクサーをリセットしても索引に残る（Microsoft Learn の記載）。この教材のデータソースは、最初から設定してある
- 更新の検出は、blob の最終更新日時を使う。変わっていない blob は、基本的には取り込み直さない。ただし、直近に取り込んだ最新のファイルは、変更がなくても、もう一度処理されることがある（実測）。そのため、インデクサーの「処理した文書の数」は、変更があったかの目印にしない
- インデクサーが実行中のとき、`run_indexer` は 409（実行中）で断られる。スクリプトは 10 秒待って、頼み直す。元に戻す（`cleanup.py`）は、実行中のインデクサーが終わるのを待ってから、文書を変える
- インデクサーの状態を取れなかったとき（通信の失敗）は、待ってやり直す。やり直しても取れなければ、止まる。取れなかったのを、「前の実行が終わった」と取り違えない
- 元に戻したあと、全部の文書のチャンクが索引に入ったかを確かめる。入っていなければ、止まって案内する（元に戻したと言わない）
- スキャンを置き直すと、OCR が走る（チームの Foundry に課金される。数件ならわずか）
- 17 の最中に、ほかの人が検索すると、途中の状態が見える。元に戻すまでの時間は、ふつう数分

## 発展

- ネイティブの論理削除（`NativeBlobSoftDeleteDeletionDetectionPolicy`）：Storage の Blob の論理削除を有効にして、このデータソースの削除の検出を切り替えると、blob を普通に消すだけで、インデクサーが索引から消す。印を付ける手順は要らない。代わりに、Storage 側の設定（論理削除の有効化、保持期間をインデクサーの実行間隔より十分長くする、Blob のバージョン管理は使わない）が要る。この教材は、Storage 側の設定が要らない方式（`IsDeleted`）を使っている
- 版を名前に入れて、別の blob として置く（`JOB-REQ042-v1.pdf` と `JOB-REQ042-v3.pdf` を並べる）と、旧い版も検索に出続ける。「どの版か」を欄に持たせて絞る設計もある
- 復元：`IsDeleted` を `false` に戻し、最終更新日時が前回のインデクサー実行より新しいことを確かめて、インデクサーを動かす
