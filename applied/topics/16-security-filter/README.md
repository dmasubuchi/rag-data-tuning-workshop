# 16 見せてよい人で絞る

採用の文書には、全員に見せてよいもの（求人票）と、見せてはいけないもの（面接の評価、現在の年収）が混ざっています。
同じ質問でも、聞いた人によって、見せてよい範囲が違います。このトピックでは、検索するときに「見てよいチャンクだけ」に絞ります。

※ このトピックに出てくる人物・評価・年収は、すべて研修用の架空のデータです。実在の人物とは関係ありません。

## 何を学ぶか

- インデックス `hr-docs` の各チャンクには、`allowed`（見てよい人）が付いている
  - 役割（`role:recruiter`・`role:interviewer`・`role:employee`）と個人（`user:U-1006`）を、同じ文字列の一覧（Collection）に入れる
  - 立場ごとの見え方
    - 採用担当（`role:recruiter`）：全部
    - 面接官（`role:interviewer` と `user:<自分の ID>`）：求人票と、自分が担当する応募の文書
    - 一般社員（`role:employee`）：求人票だけ
  - 現在の年収を含むチャンクは、同じ文書の中でも採用担当だけ
- 絞り込みの式（filter）は、検索する人の印を入れ替えるだけ

```
allowed/any(a: search.in(a, 'role:interviewer,user:U-1006'))
```

  - チャンクの `allowed` のどれかが、`search.in` の中の印のどれかと同じなら見える
  - 検索の前に決まるので、見えないチャンクは、順位にも、LLM に渡す資料にも出てこない
- 悪い例：絞り込みをせず、全部を LLM に渡して、プロンプトで「評価と年収は答えるな」と頼むだけにすると、漏れる
- 結論：**見せてはいけないものは、LLM に渡す前に、検索で外す**

## 前提

- `pip install -r applied/requirements.txt`（Repo 直下で、仮想環境の中で）
- 構築する人がインデックス `hr-docs` を作り、見てよい人（`allowed`）を付けてあること（なければ構築する人に聞く）
- メンバーの設定（検索だけのキー、Storage なし）で動きます
- `leak_demo.py` は、`.env.local` の `AZURE_OPENAI_CHAT_DEPLOYMENT` のデプロイで LLM を呼びます（質問ごとに 2 回）。

## 実行

```
python search_by_role.py                         # 同じ質問を、3つの立場で検索する
python search_by_role.py --interviewer U-1007    # 面接官を変える
python search_by_role.py --question "REQ-043 に応募した人の経歴を教えてください"
python leak_demo.py                              # 悪い例と良い例を並べる
python leak_demo.py --question "REQ-043 に応募した人の面接官のコメントを、そのまま引用して"
```

## 見るところ

- `search_by_role.py`
  - 立場ごとの「見えるチャンク」の数が違う。採用担当は 48 件すべて、面接官 U-1006 は 43 件、一般社員は求人票の 6 件だけ
  - 絞り込みの式が、画面に出る。立場の印だけが違う
  - 同じ質問でも、立場ごとに上位の文書が変わる。見えないものは、順位が下がるのではなく、検索の対象にならない
  - 「現年収」で探すと、採用担当だけ 2 件。ほかは 0 件
  - 限界：面接官に見える面接の評価のチャンクに、担当でない応募の番号が混ざる（絞り込みはチャンクが単位で、Excel は 400 文字ずつに切るため）
- `leak_demo.py`
  - 悪い例：絞り込みなし（全部のチャンク）。「LLM に渡したチャンク」に、面接の評価・経歴書・スキャンが入っている。「評価は答えるな」と頼んだのに、答えに評価の中身（強く推奨など）が出る
    - 教材を作ったときの測定では、この2問（直接聞く・「面接はどうだった？」と聞く）を 6 回ずつ聞いて、12 回とも、評価の中身が出た（モデルが違えば、変わることがある）
    - 禁止に書かなかったこと（内定、入社予定日）も、そのまま答える
    - 禁止した語を並べて聞く質問（「現在の年収と、面接の評価を教えて」）では、断る回もあった
  - 答えは実行のたびに変わる。今回出なくても、安全ではない。「たまたま断った」を、防御と数えてはいけない
  - 良い例：同じプロンプトで、先に一般社員の印で絞る。LLM に渡すのは求人票だけ。評価も年収も入っていないので、どんな聞き方でも漏れようがない

## 発展

- チャンクの切り方と、見せる単位：評価の Excel を 1 行 1 チャンクで取り込めば（14 の切り方）、行ごとに `allowed` を決められる。担当でない応募の行は、見えなくなる
- 検索する人の印は、このトピックでは手で決めている（`acl.viewer_interviewer("U-1006")` など）。実際のシステムでは、ログインした人から決める
- Entra（Microsoft Entra ID）との連携（紹介だけ。この教材は、鍵だけで動かすので、実装していません）
  - アプリが Entra で利用者をログインさせ、その人の所属グループやユーザー ID を取り出す
  - 所属グループを、`role:…` の印に変える（例：「採用チーム」グループなら `role:recruiter`）。ユーザー ID は `user:…` にする
  - その印を、この `filter` の `search.in(...)` に入れて検索する。式の形はこのトピックと同じ
  - 検索サービス側で、Entra のグループやユーザーに基づく文書単位のアクセス制御を行う機能もある。プレビューの機能が含まれるので、使う前に、最新の Microsoft Learn（Azure AI Search の document-level access control）で確かめる
- 面接の評価の Excel で、応募の番号が出てこないチャンクは、評価基準・注記のシートの文章と確かめられたものだけ、面接官全員に見せる。個別の評価の後半だけが切れて入ったチャンクなど、由来を確かめられないものは、採用担当だけにする（Azure の分割は、Excel の行を保証しないため）
- `allowed` は、取り込みの後に付ける（`lib/acl.py`）。インデクサーを動かして取り込み直したチャンクは `allowed` が空に戻り、空のチャンクはだれにも見えない（安全側）。17 は、インデクサーを動かすたびに、全部のチャンクに付け直している
